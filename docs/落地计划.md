## 0. 这份文档要解决的问题

用户提出的原话是：

> 现在的安装方式太复杂了，我想要发布的成果物直接可以使用，不用安装各种依赖，并且能够跨平台使用。

把这句话拆开，它其实是**两个独立的问题**，而它们在难度上相差很大：

| # | 问题 | 难度 | 本计划的位置 |
|---|---|---|---|
| 1 | **不用安装各种依赖** —— 现在要装 Python、ffmpeg、还要 `uv tool install` | 高 | P0 + P1（去掉 ffmpeg）+ P2（打包） |
| 2 | **跨平台** —— 现在只有 macOS 上验证过 | 中 | P2（CI 矩阵）+ P3（分发渠道）+ P4（`--login`） |

**关键判断：ffmpeg 就是「各种依赖」里最难缠的那一个。**
PyInstaller 能把 Python 解释器和 pip 依赖一起打进单文件，唯独 ffmpeg 是外部二进制——它要么要求用户预装（问题没解决），要么打进产物（每个平台 +40~80 MB，还要背上 LGPL/GPL 的分发义务）。所以**先去 ffmpeg，再打包**，顺序不能反。

## 1. 目标与非目标

### 1.1 目标

- **G1** 交付物在三平台都是「下载一个文件 → 直接跑」，零外部依赖
- **G2** 合并质量**不低于**当前的 ffmpeg 路径：无损、音画同步、可拖动进度条
- **G3** 产物格式从「ffmpeg 能产出的」变成「我们自己控制的」，因此可以做得比 ffmpeg **更好**（见 §3.4）
- **G4** 每个平台有官方分发渠道（Homebrew tap / Scoop bucket / curl 脚本）

### 1.2 非目标（本计划明确不做）

- ❌ **不重写成 Go/Rust**。收益是启动快 + 体积小，代价是把 7095 行已验证的 Python 全部重写。当前痛点不在语言。
- ❌ **不做 GUI**。CLI 是产品定位，不是过渡形态。
- ❌ **不追求 Windows arm64**。PyInstaller 对该目标支持薄弱，投入产出比极差。
- ❌ **不加新依赖**。纯 Python 合并的整个意义就是让依赖表**变短**，不是变长。

## 2. 现状基线（全部实测，可复现）

样片：`BV17wpp6SEe9`（17:42，480P AVC + 192K AAC）。复现命令：

```bash

```

| 项 | 视频分片 | 音频分片 |
|---|---|---|
| 文件大小 | 108,457,377 B | 20,082,340 B |
| `ftyp` | `iso5` / `iso5,iso6,mp41,dash` | 同左（**完全一致**） |
| 片段数 | 213 | 212 |
| `mdhd` timescale | 16000 | 44100 |
| 每片时长 | 80,000 ticks = **5.000 s** | 221,184 ticks = **5.0146 s** |
| 样本总数 | **31,834** | **45,700** |
| 编解码 | `avc1` + `avcC`/`colr`/`pasp`/`btrt` | `mp4a` |
| 编辑列表 | `elst media_time=1600`（**0.1 s**） | `elst media_time=0` |
| `mdat` 占比 | 99.62% | 98.58% |

**当前 ffmpeg 路径的参考产物**（`-c copy -movflags +faststart`）：

- 129,157,466 B，其中 `moov` 1,314,840 B 置于文件头
- `mvhd` v1，timescale **7,056,000**（= lcm(16000, 44100)），duration 1061.154 s
- 包总数 **77,534** = 31,834 + 45,700 —— **与两条源流的样本数之和完全相等**，证明 remux 是无损且不丢样本的
- 耗时 **0.255 s**（129 MB）——**合并从来不是性能瓶颈**，去掉 ffmpeg 的动机纯粹是「依赖」，不是「速度」

这个 77,534 的数字很重要：它给出了一个**无需人工判断的对拍基准**（见 §5.1）。

## 3. 关键技术判断

这三条实测结论决定了「纯 Python 合并」是可行的，而不是一场赌博。

### 3.1 `default-base-is-moof` 已置位 → 移动片段不需要重算偏移

```
tfhd size=28 flags=0x020038 track_id=1 [default-base-is-moof]
trun size=1824 v0 flags=0x000b05 sample_count=150 data_offset=1912
```

`0x020000` 就是 `default-base-is-moof`。它的含义是：`trun.data_offset` **相对于本 `moof` 盒子的起点**，而不是相对文件绝对位置。

**这一条是整个方案的支点**：只要 `moof` + `mdat` 成对搬运、内部字节不变，偏移就永远正确。如果这个标志没置位，每次移动片段都要遍历 `trun` 重算绝对偏移——代码量和出错面都会成倍上升。

### 3.2 两条流都是「单轨 + 轨道号 1」→ 重编号问题（被 P0 的产物形态消解）

两个文件的 `moov` 里 `tkhd.track_id=1`、`mvex/trex.track_id=1`、每个 `tfhd.track_id=1`。

**如果输出分片式 MP4**，音频轨必须改成 **2**，且**四处都要改**：`tkhd.track_id`、`trex.track_id`、`mvhd.next_track_id`（→3），以及**每一个音频 `tfhd.track_id`**。漏掉 `tfhd` 是最典型的坑：文件能打开，但播放器会把音频样本算到视频轨上，表现为「时长对但没声音」或直接报错。好消息是 `tfhd.track_id` 是定长字段，原地改写不改变盒子大小。

**但 P0 实测确定输出形态应为渐进式 MP4**（§3.5），此时 `mvex`/`trex`/`tfhd`/`moof` **全部不会出现在产物里**（ffmpeg 的参考产物同样没有 `mvex`），于是「重编号」这个整类问题自动消失——只剩 `tkhd.track_id` 一处要写。这是选渐进式而非分片式最实在的收益。

### 3.3 编辑列表必须原样保留

视频的 `elst media_time=1600`（0.1 s）是 B站用来对齐音画的偏移。ffprobe 对源分片报告的首包是 `pts=0, dts=-1600`——这个 `-1600` 正是 `media_time` 被应用的结果。

ffmpeg 的做法是**保留 `media_time=1600` 不动**，样本表里的原始解码时间也原样搬运。我们的实现照做即可，**不需要做任何时间戳重基（rebasing）**。这也让实现简单了一个数量级。

### 3.4 顺带能拿到的两个好处

去掉 ffmpeg 不只是「少一个依赖」，还顺手解决两个现存问题：

1. **HEVC 的 `hvc1` 标签** —— 现在是靠给 ffmpeg 传 `-tag:v hvc1` 来让 QuickTime 认。我们直接写 `stsd` 时按平台写对的标签即可，不必再依赖外部工具的开关。（实测 B站 HEVC 分片本身就已是 `hvc1`，这一条退化为安全网。）
2. **进度可见** —— ffmpeg 是个黑盒，合并阶段只能转圈。自己写就能按片段报进度。

### 3.5 P0 探针的四条新增结论（决定正式实现怎么写）

这四条在计划阶段是不知道的，全部由 P0 用真实数据打出来，**正式实现必须照此办理**：

**① 输出形态：渐进式 MP4（单 `moov` + 完整样本表），不是分片式。**

ffmpeg 的参考产物是渐进式的，且**逐包对拍在 6 组样片上全部通过**——说明从 DASH 分片还原出完整样本表这一步是无损的。渐进式因此不是「有风险的选项」，而是**经过验证的首选**，§5 P1.5 里的降级分支可以删掉。额外收益见 §3.2。

**② 交织顺序必须按「编辑列表校正后的 DTS」全局归并，同一时刻视频优先。**

这是 P0 里唯一一次真正的失败：按**片段粒度**轮流写（视频 5 秒 → 音频 5 秒）文件完全合法，但 77,034 个包里有 77,078 个与 ffmpeg 不同。规则是：

```
比较 (dts − elst.media_time) / timescale   ← 注意用**显示**时间轴，不是解码时间轴
```

用整数交叉相乘比较（`dts * (L // timescale)`，`L = lcm(各轨 timescale)`），避免浮点误差；同值时按轨道序号排，视频轨在前。实测这一条让 77,534 个包**全部**对齐。

> 容易走错的地方：用**原始** `dts` 排序是不对的。视频的 `elst media_time=1600` 必须参与计算——不参与的话音频会在开头就插进来。

**③ `ftyp` 必须按编解码器重新合成，不能照抄某一条流。**

`ftyp` 只是一句「本文件兼容哪些规范」的声明。B站 AV1 分片的 `ftyp` 是 36 字节（多带一个 `av01` 品牌），AVC/HEVC 是 32 字节，而音频流**永远**是 32 字节——所以「两条流的 `ftyp` 逐字节相同」这个前提根本不成立，早期实现直接在这里抛了错。正确做法是仿照 ffmpeg：`isom` 主品牌 + `iso2` + 编解码器品牌 + `mp41`，丢掉 `dash`。

**④ 样本必须按「文件里连续同轨」合块，不能逐样本一块。**

逐样本一块（`stsc` 只有一条记录）写起来最省事，也能播，但 `stco` 会白占**每个样本 4 字节**。实测代价：单轨视频文件的 `moov` 比 ffmpeg 大 125,720 B，音频文件大 182,454 B。按连续段合块后，六组样片的体积差全部收敛到 **62–1,620 字节**（差异仅来自 `ftyp` 品牌顺序与时长量化）。

> 这条还暴露了实现上的一个顺序要求：块的**个数**会影响 `moov` 长度，进而影响所有偏移。所以必须**先分块、再算偏移**——先按占位偏移构造一次 `moov` 拿到长度，再回填真实偏移。

#### P0.2 产物形态（与计划阶段的设想不同）

计划里设想的是**分片式输出**（保留 `moof` + 重编号 `tfhd`/`trex`）。实测改为**渐进式 MP4**（单个 `moov` + 完整样本表），理由是它与 ffmpeg 参考产物形态一致，且逐包对拍全通过。收益见 §3.2 与 §3.5 ①。

#### P0.3 三重量化验证结果

| 组 | 逐包对拍（主力判据） | AVFoundation 逐帧 | 体积差 vs ffmpeg |
|---|---|---|---|
| 480P AVC | ✅ 77,534 包全同 | ✅ 逐行一致 | −114 B |
| 1080P HEVC | ✅ 77,534 包全同 | ✅ 逐行一致 | −110 B |
| 1080P AV1 | ✅ 77,534 包全同 | ✅ 逐行一致 | −114 B |
| 竖屏 | ✅ 2,716 包全同 | ✅ 逐行一致 | −62 B |
| 只有视频 | ✅ 31,834 包全同 | ✅ 单轨可播 | −1,620 B |
| 只有音频 | ✅ 45,700 包全同 | ✅ 单轨可播 | −350 B |

- **逐包口径**：`ffprobe -show_packets -show_entries packet=stream_index,pts,dts,size,flags` 的完整序列逐行比对，六组**全部完全相同**
- **播放器口径**：`/tmp/avtest` 用 `AVAssetReader` 真解码，报告 `playable` / `decodable` / 解码帧数 / 解码字节数。六组均与 ffmpeg 产物**逐行一致**；`qlmanage` 缩略图两者 md5 相同（`e820cd53aa27fcaff3a3fdd023b71242`）
- **性能**：230 MB 合并耗时 **0.30–0.42 s**（ffmpeg 0.255 s）→ 去掉 ffmpeg 不会变慢
- **已知且接受的偏差**：容器时长报 1061.134 s（`mvhd` 时间刻度沿用源文件的 1000 并向上取整），ffmpeg 报 1061.1333125 s（它把 `mvhd` 升到 v1 且用 timescale 7,056,000）。差 **0.7 ms**。`stts` 是精确的，帧级时序与音画同步不受影响。要消灭这 0.7 ms 需把 `mvhd`/`tkhd`/`elst` 升到 version 1（32 位字段存不下 7,056,000 × 1061 s），**判定为不值得**

#### P0.4 失败与修复记录

| 现象 | 根因 | 修复 |
|---|---|---|
| 77,534 包里 77,078 个不同（首处 `ref=1,0,0,440` vs `mine=0,533,533,149`） | 按**片段粒度**交织，且用**原始** `dts` 排序 | 改为按 `dts − elst.media_time` 全局归并（§3.5 ②） |
| `ValueError: 两条流的 ftyp 不一致` | AV1 分片 `ftyp` 是 36 B（多带 `av01`），而「两条流 `ftyp` 相同」这个前提不成立 | 按编解码器重新合成 `ftyp`（§3.5 ③） |
| 单轨文件 `moov` 比 ffmpeg 大 125,720 B / 182,454 B | 逐样本一块，`stco` 白占每样本 4 字节 | 按连续同轨段合块（§3.5 ④） |
| `AssertionError: (1314734, 1037486)`：构造 `moov` 两次长度不一致 | 块**个数**依赖真实布局，占位时误用「每样本一块」 | 先分块 → 占位用真实块数 → 再回填偏移（§3.5 ④ 末） |
| `_parse_trun() takes 4 positional arguments but 5 were given` | `tfdt` 的解码时间需要传进 `trun` 解析 | 把 `decode_time` 作为参数传入 |
| `patch_mdhd` / `patch_mvhd` 写错偏移 | v0/v1 的字段宽度不同（duration 在 24 或 32） | 按 `raw[8]` 的 version 分支 |

#### 首次发版踩到的坑（v0.8，macOS 两个已修复；Windows 仍在查，v0.9 更正了一次错误诊断）

第一次打 tag 之后，CI 挂在那儿 40 分钟"排队"。真相是**两个互不相干的故障**，而且都
属于"看起来像 A、实际是 B"那一类：

**坑一：`macos-13` 已下线，但它不报错。**
GitHub 下线了这个镜像（[changelog](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/)），可**标签还在、语法也合法**——于是 job 不失败，只是永远等不到机器。症状是整个 run 停在 `queued`，`publish` 因为 `needs: build` 永不触发，**日志里一个字都没有**。判据是去看 **job 列表**（不是 run 状态）：另外四个 job 早就 `completed` 了，只有它孤零零挂着。替代标签 `macos-15-intel`。

**坑二：Windows job 挂在冒烟测试上，但看起来像合并内核坏了。**
原脚本跑 `bclaw --check` 再 `grep "自检通过"`，Windows 上整个 job 失败，报"✗ 合并内核自检未通过"。**失败信息把人指向内核，而内核根本没问题。**
修法是**给脚本一个专门用来判读的入口**，而不是把 grep 写得更宽容：新增隐藏的 `bclaw --selftest`——纯 ASCII 输出（`merge self-check: OK`）、不碰网络、退出码即结论。三个平台判读方式完全一致，以后再加平台也不用重新想这件事。
> **当时的诊断是错的，此处如实更正。** 曾认定"Windows 控制台代码页不是 UTF-8，grep 匹配不上汉字"。**PyInstaller 冻结后的 `sys.stdout.encoding` 恒为 `utf-8`**（rich 遇到 `UnicodeEncodeError` 是**重新抛出**而不是吞掉，所以真有编码问题会是崩溃而非静默），中文输出在 Windows 上并不会丢。改 `--selftest` 之后 Windows **照挂**，正是这条错误诊断的第一个反证。`--selftest` 保留下来了，但理由换成更站得住的那个：它是**给脚本判读的信号**，不是给人读的文案。

**坑三（v0.9 更正：这个诊断是错的，留下过程作反例）**
曾经认定根因是"Windows 检出拿到 CRLF 的 `build.sh`，bash 在第三行就死"，并据此补了 `.gitattributes`。**CI 自己把这个假设证伪了**：

| run | sha | 有 `.gitattributes`？ | Windows 结果 |
| --- | --- | --- | --- |
| #4 | `414d3e88` | ❌ 没有 | 失败，但 annotation 里明明有 `platform detected: uname -s='MINGW64_NT-10.0-26100'` |
| #5 | `2c3d3c42` | ✅ 有 | 失败，位置与 #4 **一模一样，一字不差** |

#4 发生在 `.gitattributes` 存在**之前**，脚本却已经在 Windows 上跑起来了；补上之后失败在同一处。等于做了一次干净的对照实验，换行符假设就此出局。

`.gitattributes` 仍然保留，但它防的是**另一类**问题，与本次故障无关：`core.autocrlf` 在不同机器上取值不同，某个人的检出真的会得到 CRLF 的 shell 脚本，而症状是

```
build.sh: line 19: : command not found
build.sh: line 19: set: pipefail: invalid option name
```

错误信息里既没有 "windows" 也没有任何指向换行符的线索。CI 上恰好没踩到，不代表下一个人在别的机器上踩不到。本地一行可复现：`git show HEAD:packaging/build.sh | sed 's/$/\r/' > /tmp/b.sh && bash /tmp/b.sh`。

**坑三的真正结论：Windows 死在 PyInstaller 的 EXE 阶段，而且没留下 traceback。**
两个 run 的 annotation 都停在同一个位置：

```
INFO: checking PYZ → Building PYZ … completed successfully.
INFO: checking PKG → Building PKG (CArchive) bclaw.pkg completed successfully.
INFO: Bootloader D:\a\...\PyInstaller\bootloader\Windows-64bit-intel\run.exe
INFO: checking EXE          ← 最后一行，然后 exit code 1
```

`checking EXE` 出自 `PyInstaller/building/datastruct.py:169`（`Target.__postinit__`），而紧随其后的 `Building EXE because EXE-00.toc is non existent`（同文件 173 行）**没有出现**——对照本机 macOS 的成功日志，`INFO: Building EXE from EXE-00.toc completed successfully.` 是正常会有的。所以崩点在进入 `EXE.assemble()` 之前或刚进入时，且**没有 Python 异常**（否则会有 traceback）。

两个候选解释，各配一个开关（都已加进 `build.sh`）：
1. 输出还压在缓冲区里没落盘 → `"$VENV_PY" -u`
2. PyInstaller 在 Windows 专属的图标/清单/资源处理里**硬崩**——那段是 ctypes 直接调 Windows API，访问违例只会给出进程级退出码，不会产生 Python 异常 → `PYTHONFAULTHANDLER=1` 把致命信号变成可见回溯

**另一个把调查拖长的原因：诊断通道本身不够用。** 原先把 `tail -40` 的每一行都发一条 `::error::`，而 GitHub **每个 step 只保留约 10 条 annotation**——真正的报错被 `checking PYZ` 这类进度行挤掉了。现在整段尾部压成**一条**（换行写 `%0A`、`%` 转 `%25`），并且**优先从严错那一行开始截**而不是死板取最后 N 行。

顺带修掉的第四个坑：`build.sh` 自己的开关原本也叫 `--check`（意思是"只构建不归档"），和 `bclaw --check` 撞名，已改名 `--no-archive`。

**守卫**：新增 `tests/test_packaging.py`，把这几件事各写成一条断言——runner 标签、冒烟测试用 `--selftest`、变量后面不能紧跟全角字符、`.gitattributes` 钉住了 `*.sh` 的 LF、**工作区里的 `*.sh` 此刻真的不含 CRLF**（前一条守"规则还在"，后一条守"规则生效了"），以及 **`annotation_tail` 的转义**（`%`→`%25`、换行→`%0A`、且必须从报错那行开始截）。变量那条是因为 `$VAR（` 这个 bash 陷阱在 `build.sh` 里**踩了两次**——第一次修完就以为记住了，第二次照踩。转义那条是因为那个函数**只在 CI 失败的那一刻执行**，本地永远走不到，坏掉不会有任何征兆。凡是"修完还会再犯""坏了看不见"的坑，就不该再靠人记得。

#### P4 实测报告（v0.8）

**三个平台的方案互不相同，不是同一个东西换个名字**——这是本次改动最要紧的一条：

| | 密钥来源 | 算法 | 代价 |
|---|---|---|---|
| macOS | 钥匙串口令 | `PBKDF2(saltysalt, **1003**)` → AES-128-CBC，IV 为 16 个空格 | 会弹一次授权框 |
| Linux | gnome-keyring 口令，取不到则 `peanuts` | `PBKDF2(saltysalt, **1**)` → 同样的 CBC | 无 |
| Windows | `Local State` 里被 DPAPI 保护的 32 字节密钥 | **AES-256-GCM**（12 字节 nonce + 密文 + 16 字节 tag） | 只能同一个 Windows 用户解开 |

**Linux 的迭代次数是 1，不是 1003。** 这是整个改动里最容易抄错、且**错了不会报错**的地方：照抄 macOS 的参数照样能跑完，只是解出来一堆乱码。测试 `test_linux_derives_with_one_iteration_not_a_thousand` 同时断言"等于 1 次"和"不等于 1003 次"，把两个方向都钉住。

**`v20`（Chrome 127+ 的 App-Bound Encryption）：明确不支持，但要认出来。** 正规解法只有"从 Chrome 进程里读内存"这类做法——既不稳定，也和恶意软件的手法没有区别，本工具不做。关键在**提示必须区分两种处境**：

- 库里没有 B站的 Cookie → 「去浏览器登录一次」
- 库里有、但是 `v20` → 「它登录过，只是我们解不开，**去登录也没用**」

代码里用一个专门的 `_AppBound` 异常把这两条路分开，因为给错提示会让人白跑一趟。混合场景（一部分 `v10`、一部分 `v20`）会**保留能解的那些**，而不是整体放弃。

**坦白：Windows 与 Linux 的路径没有在真机上跑过。** 本机是 macOS，只能验证：① macOS 现有行为无回归（Chrome + Firefox）；② 平台分派逻辑用 `monkeypatch` 切 `_platform()` 后逐条断言路径、派生参数与 GCM 往返。**真实的 Windows / Linux 机器上第一次跑 `--login` 仍可能出问题**，这也是 P3 验收第 2 条（三平台各从零装一次）必须真做的原因。

## 6. CI 矩阵

PyInstaller **不能交叉编译**，每个平台必须在自己的 runner 上构建。

| 目标 | runner | 产物名 |
|---|---|---|
| macOS arm64 | `macos-14` | `bclaw-macos-arm64.tar.gz` |
| macOS x64 | `macos-15-intel` | `bclaw-macos-x64.tar.gz` |
| Windows x64 | `windows-latest` | `bclaw-windows-x64.zip` |
| Linux x64 | `ubuntu-22.04` | `bclaw-linux-x64.tar.gz` |
| Linux arm64 | `ubuntu-24.04-arm` | `bclaw-linux-arm64.tar.gz` |

**四个必须记住的约束**

1. **Linux 要在最老的受支持 LTS 上构建**。glibc 是**向前兼容、向后不兼容**的：在 24.04 上编出来的二进制在 22.04 上会因为 glibc 太新而跑不起来。反过来则可以。所以 x64 选 `ubuntu-22.04`。
2. **Windows arm64 不做**。
3. **macOS x64 用 `macos-15-intel`，绝不要写回 `macos-13`。** 那个镜像 GitHub 已下线（[changelog](https://github.blog/changelog/2025-09-19-github-actions-macos-13-runner-image-is-closing-down/)），但**标签还在、语法也合法**——于是它不报错，只是永远等不到机器。症状是整个 run 一直停在 `queued`（**不是失败**），`publish` 因此永不触发，而日志里一个字都没有。第一次发版就在这上面空等了 40 分钟。判据：去 run 详情页看 **job 列表**而不是 run 状态——四个 job 早就 `completed`，只有那个标签孤零零挂在 `queued`。
4. **shell 脚本由 `.gitattributes` 钉成 LF。** 这是**防御性**的，不是任何已发生故障的根因——曾经这么写过，被 `414d3e88`（无 `.gitattributes`，Windows 却正常跑起脚本）那次运行证伪。`core.autocrlf` 在不同机器上取值不同，某个人的检出不巧就会拿到 CRLF 的 shell 脚本，bash 读到 `set -euo pipefail\r` 直接退出（`set: pipefail: invalid option name`），而错误信息完全不指向换行符。零成本，留着。见 §5 P3 的"坑三"。
5. **冒烟测试用 `--selftest`，不要 grep `--check` 的中文输出。** 判读不该依赖人读的文案：文案一改 CI 就红。`--selftest` 是给脚本判读的信号——纯 ASCII、不碰网络、退出码就是结论。
   （**不是**因为"Windows 代码页不是 UTF-8、中文会丢"：PyInstaller 冻结后 `sys.stdout.encoding` 恒为 `utf-8`，那条早期诊断是错的，见 §5 P3 "坑二"的更正。）

## 7. 各平台安装步骤（实现后长什么样）

> **暂时都用写死 tag 的 URL。** `/releases/latest` 会跳过**预发布**，而验证期发的正是预发布——写 `latest` 会让用户的第一条命令直接 404，且报错看起来跟「项目没发版」一模一样。三平台各自从零装过一次之后，再把 URL 里的 `releases/download/v0.1.0` 换成 `releases/latest/download`。

**macOS**
```bash
# Homebrew tap 尚未建立，先用脚本
curl -fsSL https://github.com/zhangjinluuu/bili-claw/releases/download/v0.1.0/install.sh | sh
```

**Windows（PowerShell）**
```powershell
irm https://github.com/zhangjinluuu/bili-claw/releases/download/v0.1.0/install.ps1 | iex
```

**Linux**
```bash
curl -fsSL https://github.com/zhangjinluuu/bili-claw/releases/download/v0.1.0/install.sh | sh
```

> **为什么刻意都用 `curl` / `brew` / `scoop` 而不是让用户去浏览器下载？**
> 这不是风格偏好。浏览器下载的文件会**被打上隔离标记**（macOS 的 `com.apple.quarantine`、Windows 的 Mark-of-the-Web），从而触发「已损坏，无法打开」和 SmartScreen 警告。用命令行工具安装**不产生这个标记**，等于免费绕过了代码签名问题——而正式解决它需要 Apple 开发者账号（$99/年）。这是值得做 Homebrew tap 与 Scoop bucket 的**真正原因**。

## 8. 风险与回退

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| 纯 Python 合并产出「能播但不对」的文件 | 中 | 高 | §5.1 逐包对拍；P0 闸门 |
| AV1 / HEVC 的 `stsd` 结构与 AVC 不同 | 中 | 中 | P0.1 覆盖三种编码 |
| 渐进式 MP4 转换复杂度过高 | 中 | 中 | 降级为分片式 MP4 输出（P1.5） |
| PyInstaller 打包后 `cryptography` 原生扩展缺失 | 低 | 中 | P2.3 在干净目录验证；用 `--collect-all` |
| Windows 杀软误报 PyInstaller 单文件 | **高** | 中 | 已知问题，无低成本解；文档说明 + 建议用 scoop 装 |
| Chrome App-Bound Encryption 封死 Windows 路径 | **高** | 低 | **已发生**：`v20` 明确不支持，但能认出来并给出与「没登录」完全不同的提示；Firefox 与 `--cookie-file` 兜底 |
| Windows / Linux 的 `--login` 在本机无法真机验证 | **高** | 中 | 平台分派逻辑用 `monkeypatch` 逐条断言；**P3 验收第 2 条（三平台各从零装一次）必须真做**，这是唯一能发现真机问题的地方 |
| Linux glibc 倒挂 | 中 | 高 | 在最老 LTS 上构建 |

**全局回退**：若 P0 失败 → 方案 B（内嵌 ffmpeg）。若 P2 也失败 → 退回 `uvx biliclaw`（PyPI 分发），至少免去手工装 Python 依赖。

## 附录 A：验收用的对拍命令

```bash
# 1. ffmpeg 参考产物
ffmpeg -hide_banner -loglevel error -y -i video.m4s -i audio.m4s \
       -map 0:v:0 -map 1:a:0 -c copy -movflags +faststart reference.mp4

# 2. 包级指纹（逐包对拍的主力）
ffprobe -v error -show_packets -of csv=p=0 \
        -show_entries packet=stream_index,pts,dts,size,flags reference.mp4 > ref.txt
# 对自己的产物重复一次，然后 diff

# 3. 样本数必须等于两条源流之和
ffprobe -v error -show_packets -of csv=p=0 -show_entries packet=stream_index out.mp4 | wc -l

# 4. 真实播放器（不能省——ffprobe 说对不代表 QuickTime 认）
open -a "QuickTime Player" out.mp4
open -a VLC out.mp4
```

**为什么必须同时用 ffprobe 和真实播放器**：ffprobe 检查的是**结构正确性**，播放器检查的是**宽容度以外的真实可播性**。两者会各自放过对方能发现的问题——只有 ffprobe 通过，可能得到 QuickTime 打不开的文件；只有播放器通过，可能得到丢了 3 秒音频却听不出来的文件。
