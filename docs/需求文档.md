## 1. 项目背景与目标

### 1.1 背景

B站内容存在观看场景受限的问题：换设备/无网络时无法观看、收藏的视频可能因 UP 主删除或下架而永久丢失、官方 App 的离线缓存加密且只能在 App 内播放、部分视频需要大会员权限才能在线观看高清画质。用户需要一个**本地可控**的工具，把 B站视频保存为标准视频文件，用于个人离线学习与内容备份。

### 1.2 项目目标

构建一个本地运行的下载工具，实现：

1. 输入 B站视频链接（或 ID），即可下载到本地；
2. **支持清晰度选择**——既能自动取最高可用画质，也能手动指定档位；
3. 输出为**通用播放器可直接播放**的 MP4 文件（音视频已合并）；
4. 支持批量下载与中断续传，适合"贴一批链接过夜跑"的用法。

### 1.3 成功标准（可度量）

| 编号 | 成功标准 | 度量方式 |
| --- | --- | --- |
| S1 | 首次使用零配置即可完成一次下载 | 全新环境执行一条命令即产出可播放 MP4，无需读文档 |
| S2 | 输出的 MP4 音画同步、可被系统播放器与剪辑软件正常打开 | 人工抽检音画同步；`ffprobe` 确认视频流+音频流均存在 |
| S3 | 清晰度控制准确 | 指定 720P 时实际产出即 720P；请求档位不可用时给出明确提示而非静默降级 |
| S4 | 批量任务健壮 | 连续下载 100 个分 P 不崩溃；中途断网/手动中断后重启可续传，不重复下载已完成分片 |
| S5 | 下载速度跑满带宽 | 分片并发下载，在带宽允许时接近本机带宽上限（不因串行下载而变慢） |

### 1.4 与现有方案的关系（工程诚实说明）

`yt-dlp` 已经支持 B站，且已实现清晰度选择、Cookie 登录、字幕、分 P 等能力。因此本项目需要明确自身定位，否则"重复造轮子"：

| 路线 | 适用场景 |
| --- | --- |
| 直接用 `yt-dlp` | 目标是"尽快能用"，不在意交互形态与定制 |
| **自研（本项目）** | 目标是**学习流媒体协议与工程实现**、需要**定制交互**（进度展示、命名规则、目录结构）、需要 `yt-dlp` 未覆盖的产物（弹幕转换、特定元数据嵌入）、或希望不依赖第三方工具的更新节奏 |

> **决策建议**：本项目的价值在定制与学习，**不在**"比 yt-dlp 下得更多"。建议在技术方案中明确：是否复用 `ffmpeg`（强烈建议复用，见 6.4），是否参考 `yt-dlp` 的实现思路。

## 2. 名词与范围

### 2.1 术语表

| 术语 | 含义 |
| --- | --- |
| BV 号 / av 号 | B站视频的唯一标识（如 `BV1xx411c7mD` / `av170001`） |
| cid | 单个**分 P** 的内容 ID；一个视频的每个分 P 各有独立 cid，播放地址按 cid 获取 |
| 分 P | 一个投稿下的多个视频分段（如教程的第 1~20 集） |
| EP / SS | 番剧的单集 ID / 整季 ID |
| DASH | B站当前主流的流媒体协议，**音视频分离**为两条独立轨道 |
| qn | 清晰度档位编号（见 6.2 对照表） |
| fnval | 播放接口的功能位掩码，决定是否返回 DASH / 4K / HDR 等（见 6.2） |
| WBI 签名 | B站对部分接口引入的动态签名机制（`w_rid` + `wts`），缺失会被拒绝 |
| SESSDATA | 登录态 Cookie 的核心字段，决定可获取的清晰度上限 |
| 大会员 | B站付费会员，1080P 高码率 / 4K / HDR / 杜比视界 / 8K 需其权限 |
| 风控 | B站的反爬机制；触发后返回 HTTP 412 或 `-352` |
| CDN 链接 | `playurl` 返回的音视频地址，**带有效期（约 2 小时）**，过期返回 403 |

### 2.2 范围内（In Scope）

- 单视频下载（BV / av / 完整 URL / `b23.tv` 短链）
- 多 P 视频、番剧（EP / SS）、合集与收藏夹的批量下载
- **清晰度与编码格式选择**（本项目核心诉求）
- 音频提取（仅下载音频，输出 `.m4a`）
- 音视频合并为 MP4
- 批量任务队列、并发控制、断点续传、失败重试
- 可选的附加产物：封面、CC 字幕、弹幕、元数据
- 配置持久化、进度展示、结构化日志
- 登录态（Cookie）支持，用于解锁高清晰度

### 2.3 范围外（Out of Scope）

明确**不做**，避免范围蔓延与合规风险：

- ❌ 破解或绕过付费内容、充电专属视频、DRM 保护内容
- ❌ 绕过大会员权限获取本无权限的画质
- ❌ 直播流录制
- ❌ 视频去水印、二次剪辑、内容再分发
- ❌ 云端服务 / 多用户服务端（本项目为**本地单用户工具**）
- ❌ 自动登录（账号密码登录、验证码破解）；扫码登录列为 P2 可选项

## 4. 功能需求

优先级说明：**P0** = 首版必须交付（MVP）；**P1** = 第二版；**P2** = 可选/后续。

### FR-01 输入解析

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 解析用户输入的链接或 ID，识别资源类型与目标分 P |

**需求明细**

1. 支持的输入形式：
   - 完整 URL：`https://www.bilibili.com/video/BV1xx411c7mD/?p=2`
   - 短链：`https://b23.tv/xxxxx`（需跟随 302 跳转解析出真实 ID）
   - 裸 ID：`BV1xx411c7mD`、`av170001`
   - 番剧：`https://www.bilibili.com/bangumi/play/ep123456`、`ss12345`
   - 合集 / 收藏夹：`space.bilibili.com/.../channel/collectiondetail?sid=...`、`.../favlist?fid=...`（P1）
   - UP 主全部投稿（P2）
2. 必须**剥离追踪参数**（`spm_id_from`、`vd_source`、`share_source` 等），但**保留** `?p=` 分 P 语义。
3. 支持一次传入多个输入（位置参数或 `-i links.txt` 文件）。
4. 无法识别的输入必须给出明确错误（"这个链接我认不出来，支持的形式有……"），而不是静默失败或崩溃。

**验收标准**

- 给定 5 种输入形式各一例，均能正确解析出目标视频与分 P。
- 输入 `https://www.bilibili.com/video/BV1xx411c7mD?spm_id_from=333.999&vd_source=abc&p=3` 时，正确解析为分 P 3。
- 输入 `http://example.com/foo` 时报错并提示支持格式，退出码为参数错误类。

### FR-02 视频信息获取与展示

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 下载前获取并展示视频元信息，**特别是当前账号实际可用的清晰度列表** |

**需求明细**

1. 获取并展示：标题、UP 主、时长、发布时间、分 P 列表（序号+标题）、封面地址、简介（截断展示）。
2. **必须展示"当前可用清晰度"**，且区分三种状态：
   - ✅ 当前账号可直接下载的档位
   - 🔒 需要登录才能解锁的档位（如 1080P）
   - 👑 需要大会员才能解锁的档位（如 4K / HDR / 8K）
3. 展示当前请求会被实际解析到的目标档位（如"将下载：1080P60 高帧率 (HEVC)"）。
4. 提供"只看信息不下载"的模式（如 `--info` / dry-run），便于用户先确认再决定。

**验收标准**

- 对未登录用户，能明确列出哪些档位因未登录/非大会员而不可用。
- 可用档位列表**以接口返回值为准**（`accept_quality` / `accept_description`），不得硬编码假设"一定有 1080P"。

> **设计约束（重要）**：B站会对请求的 `qn` 做**静默降级**——请求 4K 但无权限时，返回的可能是 1080P 甚至更低，且不一定报错。因此**必须以最终返回的流信息为准**来判定实际下载画质，并把"请求档位 ≠ 实际档位"这一情况**显式告知用户**，不能悄悄降级。这是 FR-03 与 FR-12 的关键联动点。

### FR-03 清晰度与音视频流选择 ★核心需求

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 让用户精确控制下载哪一路视频流与音频流 |

**需求明细**

1. **四种选择方式**（优先级从低到高，后者覆盖前者）：
   - 配置文件默认值
   - 自动模式：不指定时取**当前账号可用的最高清晰度**（默认行为）
   - 命令行参数：`-q 1080` / `--quality 1080`
   - 交互模式：`-q ask` 时列出可用档位让用户选择
2. **支持"不高于"语义**：`-q 1080` 表示"在 ≤1080P 的档位中取最高可用"（而非精确匹配 1080P 否则失败）。这是能覆盖绝大多数真实场景的语义。
3. **降级策略必须可配置**，默认行为为"**自动降级 + 醒目的降级提示**"：
   - `--on-unavailable degrade`（默认）：降级到最近的可用档位，并在输出中明确标注
   - `--on-unavailable fail`：严格模式，请求档位不可用时直接报错退出（用于脚本化/自动化场景）
4. **编码格式偏好**：支持按 `AVC / HEVC / AV1` 排序偏好（如 `--codec avc,hevc`）。
   - 提供 `--codec-compat` 快捷开关：优先选择兼容性最好的 AVC(H.264)，避免 HEVC 在部分播放器/剪辑软件中无法解码的问题。
   - 需在信息展示中标注各编码的实际可用性。
5. **音频流选择**：
   - 支持选择音频档位（普通 / 高码率 / 杜比全景声 / Hi-Res 无损，见 6.2）
   - 默认自动选择最高可用音频
   - **仅音频模式**（`--audio-only`）：跳过视频流，输出 `.m4a`（不转码，直接封装）
6. **输出容器**：默认 MP4（`-c copy` 无损封装）；提供 `--container mkv` 选项——**当所选编码组合无法无损装入 MP4 时必须自动改用 MKV 或明确告警**（见 FR-05）。

**验收标准**

| 用例 | 期望结果 |
| --- | --- |
| 不指定清晰度下载一个 1080P 视频 | 得到 1080P，且是当前账号可用的最高档 |
| `-q 720` 下载一个支持 4K 的视频 | 得到 720P（而非 4K） |
| `-q 720` 但视频最高只有 480P（默认策略） | 得到 480P，且输出明确提示"720P 不可用，已降级为 480P" |
| 同上，但使用 `--on-unavailable fail` | 报错退出，退出码为"档位不可用"类，不产生文件 |
| `-q ask` | 列出可用档位并等待用户输入，选择后按所选下载 |
| `--audio-only` | 只产出音频文件，无视频流 |
| 未登录账号请求 4K | 明确告知需要大会员/登录，按策略降级或失败，绝不静默假装成功 |

### FR-04 下载引擎

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 高效、可靠地把音视频流下载到本地 |

**需求明细**

1. **并发分片下载**：使用 HTTP Range 请求并行下载，并发数可配置（默认建议 4~8，`--concurrency`）。
2. **断点续传**：
   - 下载中的文件使用 `.part` 等临时后缀，避免半成品被误认为成品
   - 记录已完成分片的元数据（如 `{文件名}.part.json` 或本地 SQLite）
   - 重新运行同一任务时校验已完成部分并**只下载缺失分片**
3. **重试与换链**（关键）：
   - 分片级重试：指数退避，默认重试 3~5 次，可配置
   - **CDN 链接过期处理**：链接有效期约 2 小时，过期返回 403 时必须**自动重新请求 `playurl` 获取新链接**并继续下载，而不是判定任务失败。这对批量长任务至关重要。
4. **限速**：提供全局限速参数（`--limit-rate`），便于用户主动降低对服务端的压力、规避风控。
5. **请求节流**：接口请求之间保持合理间隔与退避，降低触发风控（HTTP 412 / `-352`）的概率。
6. **失败隔离**：单个分 P 失败不应中断整个批量任务；任务结束后汇总报告成功/失败清单。
7. **内存占用**：必须**流式写盘**，不得把整个视频读入内存。
8. **磁盘空间检查**（P2）：下载前估算所需空间并检查磁盘余量。

**验收标准**

- 下载过程中 `Ctrl+C`，再次运行同一命令，能从断点继续（不重复下载已完成分片）。
- 人为使某个 CDN 链接失效（或断网 30 秒后恢复），任务能自动换链/重试并最终完成。
- 下载 4K 视频过程中，进程内存占用保持稳定（不随文件增大而线性增长）。
- 批量任务中某个分 P 因权限失败时，其余分 P 仍正常完成。

### FR-05 音视频合并

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 将分离的视频流与音频流合并为可直接播放的文件 |

**需求明细**

1. **依赖 ffmpeg**，使用 `-c copy` 做**无损封装（remux）**，不重新编码（保证 100% 原始画质，且速度极快）：
   ```
   ffmpeg -i video.m4s -i audio.m4s -c copy -map 0:v:0 -map 1:a:0 -f mp4 output.mp4
   ```
2. **ffmpeg 可用性检测**：启动时检测 `ffmpeg` / `ffprobe` 是否存在，缺失时给出**明确的安装指引**（如 `brew install ffmpeg`），而不是抛出难懂的异常。
3. `--no-merge` 选项：跳过合并，保留分离的原始流文件（供进阶用户自行处理）。
4. **合并后校验**：用 `ffprobe` 确认输出文件同时包含视频流与音频流、时长与预期相符；校验通过后再清理临时文件。
5. **合并失败处理**：保留原始流文件，保留完整的 ffmpeg 错误输出，提示用户手动合并命令。
6. **容器兼容性**：所选编码无法无损放入 MP4 时（如某些 AV1/HEVC 组合或杜比视界），自动改用 MKV 或明确告警。
7. **转码选项**（P2，非默认）：提供有损转码为 H.264 的选项（供剪辑兼容），必须在文档中说明画质损失。

**验收标准**

- 合并产物用 macOS 系统播放器可直接播放，音画同步。
- `ffprobe` 输出中视频流与音频流均存在，时长与视频信息一致。
- 系统未安装 ffmpeg 时，命令输出清晰的中文安装提示，退出码为"依赖缺失"类。
- 合并成功后临时文件被清理，只剩下载产物。

### FR-06 批量与队列

| 项 | 内容 |
| --- | --- |
| 优先级 | P1（基础多链接为 P0） |
| 描述 | 支持一次处理多个视频/分 P，并控制并发 |

**需求明细**

1. 输入：命令行多个位置参数，或 `-i links.txt` 链接清单文件。
2. 多 P 视频：默认下载全部分 P（`--all-parts`），或指定 `-p 1,3,5-8` 区间。
3. 任务队列：多个视频之间**有限并发**（`--jobs`，默认 1~3，避免风控与带宽争抢）；单个视频内部的音视频流可并行。
4. **重复检测**：本地记录已下载的 `(bvid, cid, qn)` 索引（如 SQLite 或 JSON），默认跳过已下载内容，`--force` 覆盖。
5. 暂停 / 恢复 / 取消（P2，交互式界面时更有意义）。
6. 任务结束输出汇总：成功 N 个、跳过 M 个、失败 K 个（含失败原因与可复现命令）。

**验收标准**

- 20 个链接的清单文件可无人值守跑完，失败项在末尾有清晰汇总。
- 重复运行同一清单，第二次默认跳过已下载项（不重复消耗流量）。
- `-p 2-4` 只下载指定的 3 个分 P。

### FR-07 命名与目录组织

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 输出文件的命名与目录结构可定制 |

**需求明细**

1. **命名模板**，支持变量：`{title}` 标题、`{bvid}`、`{aid}`、`{cid}`、`{p}` 分 P 序号、`{pname}` 分 P 标题、`{up}` UP 主、`{date}` 发布日期、`{qn}` 清晰度、`{codec}` 编码。

- 多 P 视频产出 `P01_xxx.mp4`、`P02_xxx.mp4`……顺序正确。
- 同名文件已存在时按配置策略处理，行为可预期。

### FR-09 登录态与凭据管理

| 项 | 内容 |
| --- | --- |
| 优先级 | P1 |
| 描述 | 支持携带登录态以解锁更高清晰度 |

**需求明细**

1. 凭据来源（按优先级）：
   - 命令行 `--cookie "SESSDATA=…"`（临时覆盖，优先级最高）
   - 命令行 `--cookie-file PATH`
   - 环境变量（`BILICLAW_COOKIE` / `BILICLAW_SESSDATA`，兼容旧名 `BILIDL_COOKIE` / `BILI_COOKIE` / `BILI_SESSDATA`）
   - 默认路径 `~/.biliclaw/cookies.txt`（兼容旧的 `~/.bilidl/cookies.txt`）
   - **从本机浏览器读取 Cookie（`--login`）** —— 见下方第 6 条
2. **清晰度与登录态的关系必须明确告知用户**（B站规则，以实测为准）：

   | 账号状态 | 大致可获取上限 |
   | --- | --- |
   | 未登录 | 通常最高 480P/720P（因视频而异） |
   | 已登录（普通用户） | 1080P |
   | 已登录 + 大会员 | 1080P 高码率 / 1080P60 / 4K / HDR / 杜比视界 / 8K |

3. **安全要求（硬性）**：
   - Cookie **绝不写入日志**，日志输出时做脱敏处理
   - 凭据文件权限建议 `600`，并在文档中提醒不要提交到 Git（`.gitignore` 必须包含）
   - 不在错误信息中回显完整 Cookie
4. **失效检测**：登录态过期时明确提示"登录已过期，请重新获取 Cookie"，而不是笼统报"下载失败"。
5. 扫码登录（P2，可选）。
6. **一键从本机浏览器取 Cookie（v0.4 实现，v0.6 补齐跨平台，`--login`）**：
   - 支持 **Chrome / Edge / Brave / Chromium / Vivaldi / Firefox**；默认 `auto`，按 Chrome 系优先的顺序探测
   - **三个平台的密钥方案互不相同**，必须分别实现，不是同一个东西换个名字：

     | 平台 | 密钥来源 | 算法 |
     | --- | --- | --- |
     | macOS | 钥匙串里的 "X Safe Storage" 口令 | `PBKDF2-HMAC-SHA1(password, "saltysalt", 1003, 16)` → AES-128-CBC |
     | Linux | gnome-keyring（经 `secret-tool`）；取不到则用 Chromium 的固定口令 `peanuts` | `PBKDF2-HMAC-SHA1(password, "saltysalt", **1**, 16)` → AES-128-CBC |
     | Windows | `Local State` 里被 DPAPI 保护的 32 字节密钥 | AES-256-GCM（12 字节 nonce + 密文 + 16 字节 tag），无填充可去 |

     macOS / Linux 的 CBC 路径：IV = 16 个空格，无填充 → 去 PKCS7 → **去掉 32 字节 `SHA256(host_key)` 前缀**（Chrome 130+ 的域名绑定）
   - **Linux 的迭代次数是 1，不是 macOS 的 1003**。这是整个功能里最容易抄错、且**抄错了不报错**的地方：照样跑得完，只是解出一堆乱码。单测必须同时断言「等于 1」和「不等于 1003」
   - 浏览器 profile 路径同样按平台分派（Windows 多一层 `User Data`，Linux 是扁平的 `~/.config` 名字，且用 `XDG_CONFIG_HOME`）；Firefox 的 profile 目录三平台各不相同，Linux 还要多认一层 `Profiles/`（部分发行版与 Flatpak 用）
   - **Windows 上 Chrome / Edge 127+ 的 App-Bound Encryption（`v20`）明确不支持**：那套方案把密钥交给受保护的系统服务，正规解法只有从浏览器进程读内存——既不稳定，也和恶意软件的手法没有区别。但**必须能把它认出来**：「库里有 Cookie 但解不开」和「库里没有 Cookie」要给**完全不同**的提示——前者让用户换浏览器，后者让他去登录，而后者是白跑一趟。混合场景下保留还能解出来的那些，不整体放弃
   - 写入默认路径并 `chmod 600`；**必须当场向 nav 接口验证**，只写文件不算成功
   - 验证结果要直接回答用户真正的问题：「这个账号最高能下到多高」
   - **验证失败要区分两类**：B站不认这份凭据 → 退出码 4 并提示重新登录；网络不通/探测不到 → 退出码 3，且**文件已经写好了**（重取一遍是白费功夫），提示改用 `--check` 复查
   - 拿不到密钥或依赖缺失时给可操作的提示，退出码 6；Safari **明确不支持**（私有二进制格式 + 需要完全磁盘访问权限，且只有 macOS 上有），报错说明原因而非静默失败
   - `--login` 与 `--cookie` 互斥（一个是去取新凭据、一个是手工给凭据，同时写含义不明）
   - `--login` 后接 URL 时，取完 Cookie 继续下载（一条命令完成）

   > **实现状态（v0.6）**：三条平台路径都已实现，macOS 行为无回归。**Windows / Linux 的真机验证尚未做**——平台分派逻辑用 `monkeypatch` 逐条断言（路径、派生参数、GCM 往返），但真实机器上第一次跑仍可能出问题。这是发布前必须补的一步。

**验收标准**

- 配置有效 Cookie 后，能下载到 1080P；清除 Cookie 后，同一视频的可选档位下降且状态提示正确。
- 开启 `--verbose` 时，日志中不含完整 SESSDATA 值。
- Cookie 失效时提示可操作（重新获取），退出码为"需要登录"类。

### FR-12 错误处理与用户提示

| 项 | 内容 |
| --- | --- |
| 优先级 | P0 |
| 描述 | 把底层错误翻译成用户能理解、能行动的信息 |

**需求明细**：建立错误码 → 用户提示 → 建议动作的映射表。

| 错误 | 含义 | 应给出的提示与建议 |
| --- | --- | --- |
| `-404` | 视频不存在 | 检查链接/ID 是否有效，视频可能已被删除 |
| `-403` | 权限不足 | 该内容需要登录或更高权限 |
| `-10403` | 大会员专享 | 该清晰度需要大会员，建议选择较低档位 |
| `-352` | 风控校验失败 | 降低并发/限速，稍后重试，检查 UA 与 Cookie |
| HTTP `412` | 请求被拦截（风控） | 明显降低请求频率，等待后重试 |
| `62002` / `62004` | 稿件不可见 / 审核中 | 该稿件当前无法访问 |
| `87007` / `87008` | 充电专属视频 | 不支持下载（范围外） |
| HTTP `403`（CDN） | 下载链接已过期 | **自动换链**；若仍失败提示重试 |
| 无可用 DASH 流 | 老视频可能仅有 FLV 格式 | 回退到 FLV/durl 下载方式（P1） |

**验收标准**

- 对上述每种错误，实际触发时输出对应的中文提示，而非原始 JSON 或堆栈。
- 提示中不包含完整 Cookie、不包含无关堆栈（`--debug` 时才显示堆栈）。

## 6. 技术方案建议

> 本章为技术方案说明。**技术栈已于 v0.2 选定**（Python + asyncio + CLI，见 6.4）；分层架构与接口要点为设计参考，实现时可微调。

### 6.1 分层架构（建议）

```
┌─────────────────────────────────────────────┐
│  界面层  CLI（P0） / TUI / GUI（P2）          │
├─────────────────────────────────────────────┤
│  任务编排层  任务队列、并发控制、进度上报、汇总  │
├─────────────────────────────────────────────┤
│  业务层  清晰度决策、命名模板、断点续传、重复检测 │
├─────────────────────────────────────────────┤
│  接口适配层 (adapter)  ★所有 B站 API 集中于此  │
│   view / playurl(WBI) / subtitle / danmaku   │
├─────────────────────────────────────────────┤
│  下载层  分片并发、Range、重试、换链、限速       │
├─────────────────────────────────────────────┤
│  后处理层  ffmpeg 合并、字幕转换、元数据写入     │
├─────────────────────────────────────────────┤
│  存储层  文件系统 + 下载索引(SQLite/JSON)      │
└─────────────────────────────────────────────┘
```

**关键设计原则**：接口适配层是唯一与 B站耦合的地方。B站接口属私有接口、会变更、有风控，把它关在一层里是**降低长期维护成本的核心手段**（对应 NFR-5）。

### 6.2 关键接口与参数（实现时需以实测为准）

| 用途 | 接口 |
| --- | --- |
| 视频信息（标题/分P/cid） | `GET https://api.bilibili.com/x/web-interface/view?bvid=` |
| WBI 签名密钥 | `GET https://api.bilibili.com/x/web-interface/nav`（取 `wbi_img.img_url` / `sub_url`） |
| 播放地址（DASH） | `GET https://api.bilibili.com/x/player/wbi/playurl?bvid=&cid=&qn=&fnval=4048&fourk=1`（**需 WBI 签名**） |
| 番剧播放地址 | `GET https://api.bilibili.com/pgc/player/web/playurl?ep_id=&qn=&fnval=4048` |
| 字幕 | `GET https://api.bilibili.com/x/player/wbi/v2?bvid=&cid=` → `subtitle.subtitles[].subtitle_url` |
| 弹幕 | 分段接口 `GET https://api.bilibili.com/x/v2/dm/web/seg.so?type=1&oid={cid}&segment_index=N`（protobuf）；旧接口 `list.so?oid={cid}`（XML） |

| 125 | HDR | 真彩 | 大会员 |
| 126 | 杜比视界 | Dolby Vision | 大会员 |
| 127 | 8K | 超高清 | 大会员 |

> ⚠️ 上表为**通用参考**。实际可获取档位因视频、账号、地区与时间而异，**必须以接口返回值 `accept_quality` / `accept_description` 为准**，禁止硬编码。

**fnval 功能位掩码**

| 位值 | 含义 |
| --- | --- |
| 16 | DASH |
| 64 | HDR |
| 128 | 4K |
| 256 | 杜比音频 |
| 512 | 杜比视界 |
| 1024 | 8K |
| 2048 | AV1 |

推荐 `fnval=4048`（以上全开）+ `fourk=1`，拿到完整档位后再按用户偏好筛选。

**音频档位（DASH audio qn）**：`30216`(64K) / `30232`(132K) / `30280`(192K) / `30250`(杜比全景声) / `30251`(Hi-Res 无损)

**视频编码（codecid）**：`7`=AVC(H.264) / `12`=HEVC(H.265) / `13`=AV1

### 6.3 WBI 签名机制（要点）

1. 从 `nav` 接口取 `img_url` 与 `sub_url`，各自取文件名（去掉路径与扩展名）得到 `img_key`、`sub_key`。
2. 按固定的 64 位重排表（`mixinKeyEncTab`）对 `img_key + sub_key` 重排，取前 32 字符得到 `mixin_key`。
3. 请求参数：过滤值中 `!'()*` 字符 → 按 key 排序 → 拼接为 query → 加入 `wts`（当前 Unix 秒级时间戳）。
4. `w_rid = md5(query + mixin_key)`，最终请求携带 `w_rid` 与 `wts`。
5. `mixin_key` **按天变化**，需缓存并每日刷新（建议缓存到本地，失败时重新获取）。

### 11.3 M1 实测校正（v0.3 追加）

附录 A 要求第 6 章的接口细节「实现时必须实测校验」。M1 把关键路径真跑了一遍，以下是**与原整理不符或需补充**的部分，代码以实测为准：

| 项 | 第 6 章原整理 | 实测结果（2026-10-13） | 处理 |
| --- | --- | --- | --- |
| 匿名清晰度上限 | 未明确 | **恒为 480P（qn=32）**。连测 5 个稿件（既有只提供 360P/480P 的老视频，也有提供 1080P60 的新视频），匿名一律只返回 `[32, 16]`，与片源提供哪些档位无关 | 不硬编码上限，一律以接口返回的流为准；降级提示区分「未登录」与「需要大会员」两种处境 |
| playurl 返回范围 | 疑似返回视频全部档位 | 返回的是**该账号权限内的整条阶梯**，并不按请求的 qn 截断：实测登录态请求 `qn=64` 时，返回的 `dash.video` 里**同样有 `qn=80` 的流**（80/64/32/16 各 3 个编码版本）。本次实际授予的档位在 `data.quality` 字段里；完整目录另在 `accept_quality` 字段里 | 选流时必须**自己按 qn 截断**（只取 `qn <=` 请求档位），否则 `-q 720` 会悄悄下成 1080P。反过来，请求最高档时返回的这一组流正是该账号实际可用的全集，可以直接当菜单用 |
| qn 与实际高度 | 按档位表线性对应 | 横屏视频两者一致；`accept_quality` 里出现 `116`(1080P60) 时，匿名请求它返回的仍只是 `32` | 降级判定一律在**档位空间**里做（比较标称高度或 qn 本身，qn 数值即清晰度顺序），绝不拿流的像素高度去比档位高度，理由见下一行 |
| 竖屏视频的 `height` | 未考虑 | 竖屏视频的 `dash.video[].height` 报的是**长边**：1080P 竖屏是 `1080x1440`，而不是 1080 高 | 这是踩过的坑：曾用 `height <= 标称高度` 做上限过滤，于是 `1440 <= 1080` 不成立，1080P 流被自己筛掉——**竖屏内容上"登录解锁 1080P"完全失效，请求 1080P 只下到 720P**。9:16 的 480P 报 `480x854`，同一个错误还会把 720P 请求的降级**漏报**成"没降级"。选流与降级判定全部改用 qn／标称高度后修复 |
| WBI 是否强制 | 必需 | 实测 playurl 不带 `w_rid` 也能成功，但签名实现已与官方文档示例值对上（`mixin_key` = `ea1db124af3c7062474693fa704f4ff8`） | 保留签名。B站随时可能收紧，且已验证正确，没有理由省掉 |
| nav 匿名返回 | 未提及 | 匿名请求 nav 返回 `code=-101`，**但 `data.wbi_img` 仍然有效** | 取 WBI 密钥时不能因 `code != 0` 就整体失败，否则未登录用户直接不可用 |

补充两条 M1 期间定下的实现约定：

- **严格模式（`--on-unavailable fail`）的退出码细分**：片源里**还有用户能接受、却没给的**档位 → 退出码 **4**（该去登录/开会员）；片源最高就到已拿到的那一档 → 退出码 **2**（换档位即可，登录也没用）。档位目录未知时保守取 2，不轻易断言权限问题。

  判据**不是**「请求的那个 qn 在不在 `accept_quality` 里」——`-q 720` 会请求 qn=74（720P60），而片源常把 720P 挂在 qn=64 上。按 qn 精确比对会把「该登录」误判成「档位不存在」，正好丢掉最该给的那句提示。要问的是「在用户能接受的范围内，片源还有没有更好的档位没给我们」。

  推论：`-q 1080` 的语义是「不超过 1080P 里最高的那档」，所以只提供到 720P 的视频也会给出 **4**——720P 确实是一档用户愿意要的清晰度，只是被登录挡住了。只有片源本身就只到已获得的档位时才是 2。
- **`-q max` 不构成降级**：没有明确请求档位，就无所谓"降级"；但仍会说明「该视频还提供 X、Y，需要登录/大会员」，因为用户有权知道上面还有什么。
- **`--audio-only` 不参与视频清晰度协商**：只要音频时请求最高档（qn=127）以拿到该账号权限内最好的音轨，且**不**做视频档位判定——否则 `--on-unavailable fail` 会因为视频档位拿不到而中止一次纯音频下载，而用户根本没要视频。
- **`-q ask`（FR-03 第 1 条）依赖"请求最高档才拿得到全集"这一实测结论**：交互菜单直接用 `qn=127` 返回的那组流来构建，因此**只列账号真的拿得到的档位**——把没权限的档位摆出来让人选、选完才发现下不了，比不给选更糟。菜单按「像素高度降序 → 用户编码偏好 → 码率降序」排序，第一项即最优，回车等于 `-q max`。选定后把 `QualityRequest` 收敛成一个具体的 `qn`，换链（CDN 链接过期重取）就能原样复用同一套选流逻辑。**非交互环境（管道、脚本、CI）必须立刻报错并列出可选档位，绝不等待输入**：一条自动化命令挂在那里等按键是最难排查的失败方式。
- **断点续传是否完成以 sidecar 为准，不能看文件长度**：`.part` 是按完整长度预分配的，所以"文件看着够大"完全不等于"内容完整"，唯一的凭据是旁边的 `.part.json`。`--concurrency 1` 实测：分片 0 下完、分片 1 下到一半时 Ctrl+C，sidecar 记为 `{"total": 6911006, "chunk_size": 4194304, "done": [0]}`；重跑输出「断点续传：1/2 分片已完成」，只补了分片 1，最终分片 md5 与一次完整下载**逐字节相同**（视频 `901cc948…`、音频 `d445e8bd…`），退出码 130 且 sidecar 被清理。
- **损坏的 `.part` 宁可重下，绝不复用**：把 `.part` 截短到 1MB、而 sidecar 仍声称分片 0 已完成，重跑时直接放弃续传、整体重下，产物 md5 依旧正确。代价是多花一次下载时间，换来的是「绝不产出静默损坏的文件」——播放器遇到坏文件只会黑屏或报错，用户无从分辨是下载坏了还是片源问题。

### 11.4 M1 实测追加（v0.4）

M1 收尾阶段又踩到几个实现层面的坑，记在这里以免重蹈。

| 坑 | 真相 | 处置 |
| --- | --- | --- |
| Cookie 失效时的表现 | `nav` 返回 `isLogin=false`；更麻烦的是 `playurl` 会返回 `quality=0`、`accept_quality=[]`、`dash=null`——看起来完全像"这个视频没有 DASH 流" | 动手前先查登录态：带了 Cookie 却不是登录态就报"Cookie 已失效"并给退出码 4（FR-09）。探测不到（网络抖动）时**不**断言，免得让人白换一次 Cookie |
| ffprobe 的输出流 | ffprobe 把 JSON 写到 **stdout**，ffmpeg 把诊断写到 **stderr**。共用一个只收 stderr 的 runner，`duration_of()` 会永远返回 `None` 而**从不报错** | 拆出同时收两个流的 runner。FR-05.4 的合并后校验依赖它，否则校验会静默退化成"永远跳过" |
| 模板变量名 | `{cid}`、`{pname}`、`{codec}` 是 FR-07.1 点名要的，此前并不存在 | 已补齐。`{pname}` 与 README 里已发布的 `{p_name}` 并存，不破坏已有模板 |
| FR-11.5 与 FR-09 冲突 | `--cookie` 的值就在 `sys.argv` 里，把调用原样回显会把凭据写进终端回滚缓冲和重定向的日志 | 重跑命令整条过 `redact()`；参数类错误不给重跑命令（照着再跑一遍只会得到同一个错误） |
| 整段下载失败 | 该路径没有 sidecar，半个文件续不了传（下次从头覆盖写），只是白占磁盘 | 失败即删 |

**测试方法学**：`_run` 这类"共用一个 runner"的简化，危险之处在于它让一个函数**永远不工作却永远不报错**——`duration_of` 就这样在无人察觉的情况下作废了很久。凡是解析外部命令输出的代码，都必须有一条**用真实命令跑出来**的集成测试；只打桩的话，桩里把 stdout 和 stderr 写反了也照样"全绿"。

### 11.5 浏览器 Cookie 提取的实测结论（v0.4 追加，对应 FR-09 第 6 条）

| 事项 | 实测结论 |
| --- | --- |
| 钥匙串读取 | `security find-generic-password -w -s "Chrome Safe Storage" -a Chrome` 返回 25 字节（24 字符 + 换行）。**在已解锁的会话里不需要人工点击授权框** |
| 密钥派生 | `PBKDF2-HMAC-SHA1(password, b"saltysalt", 1003, 16)` → AES-128 密钥 |
| 解密参数 | AES-128-**CBC**，**IV = 16 个空格**（`b" " * 16`），`-nopad`，解完手工去 PKCS7 填充 |
| **Chrome 130+ 的域名绑定** | 明文**前面多出 32 字节 `SHA256(host_key)`**。`encrypted_value` 前三字节为 `v10` 只说明用了这套密钥，**不代表明文就是 Cookie 值**。实测 `raw[:32] == sha256(host_key.encode()).digest()`，host 用的是带前导点的 `.bilibili.com` |
| 症状与教训 | 漏掉上一步时解出来**不是报错而是乱码**（`isascii=False`、首字符是 `U`）。是"解得出但都是乱码"这个现象把人引向域名哈希的——解密类代码必须对明文做**可判定**的断言（ASCII、字段长度），否则坏了也看不出来 |
| 交叉印证 | 解出的 SESSDATA 为 222 字符，与用户手工粘贴的 Cookie 文件里的长度完全一致 |
| 库的读取方式 | Chrome 的 `Cookies` 是 SQLite，但**运行中的浏览器会持锁**。复制一份到临时文件再打开，绝不直接读原库 |
| 到期字段 | `expires_utc` 是 Chrome 时间（1601-01-01 起的微秒）。只取未过期的行，否则会拿到早已作废的凭据 |
| Firefox | 库是明文 SQLite（`cookies.sqlite`），不需要解密；但要用 `PRAGMA key` 之外的只读方式打开 |
| Safari | `Cookies.binarycookies` 是苹果私有格式，且读取需要「完全磁盘访问权限」。**明确不支持**，报错说明原因 |

**安全处理**：写文件用 `os.open(..., O_CREAT, 0o600)` 后**再 chmod 一次**（`umask` 会削掉创建时的模式）；日志里只打浏览器名、profile 名与字段数，**绝不打印任何 Cookie 值**。

**为什么验证这一步不能省**：只把文件写下去就报成功，等于把"这份凭据到底有没有用"推迟到下一次下载才暴露——而那时用户已经以为自己配好了，看到 480P 只会去怪片源。实测中这一步立刻抓到了一个真实的装配故障：全局安装（`uv tool install`）的环境早于 `cryptography` 依赖被加入，于是 `--login` 在已经装好的命令上直接报退出码 6。**自测时必须用"用户实际会敲的那条命令"，而不是项目虚拟环境里的入口。**
